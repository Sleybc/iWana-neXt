## 1. Objetivo, alcance y autoridad

El operador registra cada dato una vez: identifica el router, describe sus interfaces y direcciones conocidas, y registra las redes desde ese contexto. El recorrido permite varias interfaces por equipo, cero o varias direcciones por interfaz y varias redes asociadas. El alta básica no exige completar todo el inventario del router.

La opción B aprobada por el usuario orienta esta propuesta. Esta aprobación de dirección no sustituye G1–G4. La consolidación y revisión de diseño concluyeron en G1–G3 (estado vigente en §13.20); los contratos runtime y las pantallas nuevas todavía no están implementados.

## 2. Personas y vocabulario

La tarea principal corresponde a administración y aprovisionamiento de red con acceso de gestión del catálogo. Una persona con lectura consulta la misma información autorizada, con sus estados y relaciones, sin acciones de modificación. El servidor conserva la autoridad de permisos y organización; ocultar botones no autoriza peticiones.

| Concepto                      | Texto de producto y significado                                                                       |
| ----------------------------- | ----------------------------------------------------------------------------------------------------- |
| Router                        | Equipo identificado por nombre y dirección de administración.                                         |
| Interfaz                      | Puerto o interfaz lógica ya existente en el router; su nombre puede ser `bridge-clientes`.            |
| Dirección de interfaz         | Dirección IPv4 con su prefijo, por ejemplo `192.0.2.1/24`; se conserva el host, no solo el bloque.    |
| Red IPv4                      | Bloque y rango administrados para asignar direcciones a servicios.                                    |
| Puerta de enlace (gateway)    | Dirección confirmada para la red; no se deduce de la IP de administración.                            |
| Sede física                   | Ubicación organizacional anfitriona, cuando exista y aplique.                                         |
| Nodo comercial                | Referencia del catálogo de cobertura comercial.                                                       |
| IP protegidas automáticamente | Direcciones que el sistema omite por reglas de infraestructura, gateway, red o difusión.              |
| IP excluidas de asignación    | Exclusiones adicionales indicadas por el operador para la red.                                        |
| Activo / Inactivo             | Estado del catálogo y elegibilidad para operaciones; no mide si el equipo está encendido o conectado. |

No usar «IP reservadas» como nombre de las exclusiones: «Reservado» ya identifica un servicio pendiente de completar. Los UUID, códigos internos y nombres de permisos no sustituyen etiquetas legibles.

## 3. Sede, cobertura y compatibilidad normativa

Se conserva la referencia opcional a la sede física de Organización. El selector presenta nombres y tipos ya existentes; una oficina puede hospedar un router, y una sede de monitoreo operativo no se convierte por ello en un nodo técnico. El selector de nodo comercial conserva su significado de cobertura y una ayuda distinta.

Conforme a ADR-044, este corte no añade `NODE` a `OrganizationSiteType`, no lo oculta como una capacidad nueva de sede y no reutiliza `CommercialNode` como `NmsNode`. No se crea un catálogo paralelo de ubicaciones o nodos desde Red.

Si no existe sede anfitriona aplicable, el router puede quedar «Sin sede física asociada». No se pide inventar una ubicación ni un contacto. Crear o modificar una sede sigue el flujo y validaciones vigentes de Organización: esta evolución no relaja contacto, coordenadas u otros requisitos. Un sitio técnico no atendido que no encaje en esas reglas requiere una decisión independiente.

Una referencia histórica inactiva sigue visible con etiqueta «Inactiva» y se conserva al guardar otro dato. El operador puede quitar una referencia mediante una acción explícita o seleccionar otra activa. La interfaz distingue: no tocar el selector conserva la asociación; «Quitar asociación» la elimina; elegir otro registro solicita una nueva asociación validada por el servidor. Una referencia ajena o inexistente se rechaza sin revelar información de otra organización.

## 4. Recorrido de router a red

### 4.1 Alta básica

El formulario de router solicita nombre, dirección de administración y métodos de control admitidos. Sede física, nodo comercial y notas siguen siendo opcionales. La nueva colección de interfaces sustituye progresivamente la referencia LAN singular; no se exige crear una interfaz para guardar el equipo.

El formulario permite «Guardar router» y «Guardar y añadir red». Ambas acciones guardan el router una vez. La segunda, tras recibir éxito e identificador del servidor, abre el alta de red con ese router fijado como contexto visible. No repite selección de equipo ni nombre del router.

Si guardar el router falla, se mantiene el formulario y no se inicia el alta de red. Si el router queda guardado y después falla cargar interfaces o guardar la red, se conserva su identificador y se muestra «El router está guardado. Completa o reintenta el registro de la red». Reintentar actúa sobre la etapa de red; no vuelve a crear el router ni simula su eliminación. Cancelar la red conserva el equipo y permite retomarla desde su detalle.

La continuación utiliza el identificador confirmado, no el nombre como clave. Ante una respuesta incierta o pérdida de conexión al guardar el equipo, el operador revisa/recarga el catálogo antes de repetir el alta; la UI no afirma éxito ni envía automáticamente otra creación.

### 4.2 Entradas alternativas al alta de red

- Desde el detalle de un router, «Añadir red» hereda y fija el router.
- Desde el catálogo de redes con filtro de un router, «Registrar red» hereda ese filtro.
- Desde el catálogo global sin router determinado, se elige un router activo una vez.

El contexto heredado se muestra por nombre, con acceso a su detalle y sin un selector redundante. Cambiar de equipo se realiza volviendo al catálogo o iniciando una nueva alta; no reasocia un borrador confirmado silenciosamente. La navegación de regreso conserva filtros, página y tamaño de página en URL según el patrón vigente.

Si el router se inactiva mientras el formulario está abierto, el servidor rechaza la nueva operación. Se conserva el borrador, se explica el cambio y se ofrece volver al equipo o al catálogo. No se elige automáticamente otro router.

## 5. Interfaces y direcciones

El detalle del router permite consultar interfaces y sus direcciones; el catálogo general conserva su tabla operativa. El resumen de interfaces sustituye gradualmente la columna singular LAN y abre el detalle existente, sin convertir cada interfaz o dirección en una columna. Redes y direcciones permanecen agrupadas por interfaz y router; los listados siguen acotados y paginados conforme al contrato de listado que publique backend.

El alta de interfaz registra su nombre y su clase descriptiva según el contrato publicado, con estado del catálogo. Una interfaz sin direcciones es válida y muestra «Sin direcciones registradas», con acción de añadir una dirección para quien pueda gestionar. Añadir una segunda interfaz o una segunda dirección conserva las anteriores. No se exige que cada interfaz tenga una IP ni se crea una red automáticamente por registrarla.

Una dirección se captura con host y prefijo. La validación de direcciones de interfaz utiliza el contrato específico que publique backend; no reutiliza el límite `/16–/30` de los pools. La UI debe admitir el caso `/32` sin interpretarlo como una red asignable del pool.

Al abrir «Añadir red» desde una interfaz activa, esa interfaz se ofrece como contexto. En las demás entradas, el operador puede asociar una interfaz activa del mismo router o usar el registro manual sin asociación cuando corresponda al caso operativo admitido por el API. Las redes históricas con interfaz nula muestran «Sin interfaz asociada» y continúan operando; no se crea una interfaz ficticia para completarlas.

### 5.1 Cambios de direcciones y datos confirmados

Editar el nombre o clase de interfaz no modifica IP, bloques, gateways ni nombres de redes ya guardados. Editar una dirección es una operación explícita que muestra el valor vigente y el propuesto; no es una consecuencia de renombrar la interfaz.

Si la IP local coincide con el gateway confirmado de una red vinculada y el servidor impide cambiar su host, la UI conserva ambos datos y explica: «Esta dirección se usa como puerta de enlace de una red. Revisa su configuración antes de cambiarla». No intenta actualizar la red en cascada ni elude la restricción mediante desasociación automática.

Un cambio admitido de prefijo conserva el gateway y CIDR de las redes existentes y muestra que debe revisarse la asociación si deja de ser coherente. Una IP nueva que ya esté reservada o activa para un servicio provoca un conflicto sin cambios parciales. No se ofrece borrado físico o retiro de direcciones en esta fase; ocultar o inactivar una interfaz no libera sus IP protegidas.

## 6. Registro asistido de red IPv4

### 6.1 Campos y origen

| Dato                       | Comportamiento del formulario                                                                               |
| -------------------------- | ----------------------------------------------------------------------------------------------------------- |
| Router                     | Heredado y visible cuando procede; elección única en entrada global.                                        |
| Interfaz asociada          | Heredada o elegida entre las activas del mismo router; nullable para compatibilidad y modo manual admitido. |
| Nombre de la red           | Sugerido y editable; no obliga a inventar un segundo nombre para avanzar.                                   |
| Dirección candidata        | Selección de una dirección registrada o captura explícita de IP/prefijo; solo propone datos.                |
| Bloque IPv4 (CIDR)         | Derivado de una entrada suficiente o capturado manualmente; pools limitados a `/16–/30`.                    |
| Puerta de enlace (gateway) | Propuesta desde una IP explícita o ingresada manualmente; visible antes de confirmar.                       |
| Rango para servicios       | Inicio y fin revisables por el operador; no se completa usando el rango de otra red existente.              |
| IP excluidas de asignación | Opcionales y adicionales a las protecciones del sistema.                                                    |
| Método por defecto         | Elegido entre métodos admitidos por el router, según contrato vigente.                                      |

### 6.2 Dos modos de entrada

**Desde una dirección con prefijo.** Mostrar las direcciones registradas de la interfaz asociada con nombre de interfaz, IP/prefijo y origen. Una sola candidata suficiente se propone visiblemente; varias candidatas no producen selección arbitraria y requieren elección explícita. El operador también puede introducir «IP del gateway con máscara» cuando ya conoce ese dato. Esta captura de red no crea por sí sola una dirección local ni una interfaz.

Seleccionar `192.0.2.1/24` permite proponer bloque `192.0.2.0/24` y gateway `192.0.2.1`; seleccionar `192.0.2.254/24` propone el mismo bloque y gateway `192.0.2.254`. El sistema no supone `.1`, no toma la IP de administración y no trata una IP local como gateway irrevocable. El origen se anuncia como «Propuesto desde…» y puede elegirse un gateway diferente antes de guardar.

Si la candidata es `/32`, no se propone un pool a partir de ella. Mostrar «Esta dirección no define el bloque para los servicios. Ingresa el bloque IPv4 y confirma la puerta de enlace». El gateway puede reutilizarse como valor propuesto, pero la coherencia con el bloque explícito debe validarse. Lo mismo aplica si el prefijo no permite un pool dentro del rango vigente `/16–/30`.

**Bloque y gateway por separado.** Permitir capturar ambos datos explícitamente sin depender de una candidata suficiente ni de inventario completo. Este modo sirve también para gateway virtual o diferente de la IP local. La asociación a interfaz, cuando se informe, sigue requiriendo coherencia de router y estado. No se exigen datos de una dirección local ficticia para registrar la red.

Cambiar de modo mantiene el borrador y sus valores editados. La UI distingue una sugerencia pendiente de un valor modificado por la persona; no limpia IP, gateway, nombre, rango o exclusiones al cambiar el selector. Si los datos dejan de ser coherentes, señala los campos que deben revisarse e impide guardar hasta resolverlos.

### 6.3 Nombre sugerido y confirmación

Con interfaz, sugerir `<nombre de interfaz> · <CIDR>`; sin interfaz, sugerir el CIDR. El nombre del equipo ya aparece como contexto y no se solicita otra vez. El nombre es opcional para el operador: si se deja vacío, el servidor aplica el nombre generado definido por el contrato y devuelve el resultado visible. La sugerencia y el nombre final respetan el máximo vigente de 120 caracteres; el contrato define la misma regla de generación para productores y consumidores.

Mientras el nombre siga siendo una sugerencia sin edición, puede actualizarse al cambiar la candidata o el bloque del borrador. Una vez que el operador escriba su nombre, no se reemplaza. Tras guardar, el nombre es un dato de la red y no se recalcula al renombrar una interfaz.

Antes de «Guardar red», el resumen muestra router, interfaz o ausencia de asociación, bloque, gateway y su origen, rango y capacidad resultante. Guardar con este resumen visible constituye la confirmación de los datos; no añade un modal obligatorio al camino habitual. La petición final contiene los valores explícitos que exige el contrato, no una orden de adivinar una configuración.

Una sugerencia no editada ni confirmada puede recalcularse al cambiar de candidata. Un gateway o CIDR editado/confirmado se conserva: la UI pide revisión si ya no concuerda y no lo sustituye. Si una dirección origen cambia durante el alta, conservar el borrador y solicitar revisión antes de guardar; no confirmar una sugerencia caducada silenciosamente.

En una red existente, CIDR y gateway mantienen la inmutabilidad vigente. Editar su interfaz o dirección de origen nunca los cambia. Un gateway virtual o introducido manualmente se presenta como valor confirmado de la red, aunque difiera de la IP física registrada.

## 7. Protecciones, exclusiones y capacidad

Presentar por separado «Protecciones automáticas» e «IP excluidas de asignación». El primer bloque es informativo e incluye dirección de red, difusión, gateway e IP locales registradas dentro del bloque que el IPAM proteja. Esas IP locales se protegen también cuando procedan de otro router de la misma organización o de una interfaz inactiva. No se copian silenciosamente a las exclusiones editables.

Las exclusiones adicionales admiten hasta 256 IPv4 separadas por comas, conforme al límite vigente. Explicar su utilidad para equipos u otros usos. Un campo vacío equivale a «Sin exclusiones adicionales». El mensaje no obliga a repetir gateway, red o difusión. Repetir una IP protegida en exclusiones no reduce dos veces la capacidad.

La capacidad se presenta con un único conteo coherente: total asignable efectivo, direcciones reservadas para servicios, activas y libres. Los bloqueos se deduplican antes de contar y las IP excluidas o protegidas fuera del rango de clientes no descuentan capacidad de ese rango. La UI consume los cálculos del servidor; no publica un segundo cálculo autorizado distinto. Si muestra una previsualización previa al guardado, la identifica como estimación y la reconcilia con la respuesta persistida.

Una exclusión fuera del bloque se rechaza junto al campo. Una exclusión que afecte una IP reservada o activa para un servicio se rechaza conservando los valores de la red y sin liberar o reasignar el servicio. El conflicto entre una IP de infraestructura y una reserva se explica como infraestructura o servicio, según la causa; no se reduce a «sin direcciones libres» ni se oculta tras una asignación alternativa automática.

## 8. Estado del catálogo y operaciones permitidas

Conservar badge de estado actual, icono y texto de acción siguiente «Activar»/«Desactivar». El estado se comunica con texto y forma, además de color. Ayuda de efecto: «Desactivar impedirá nuevas reservas; los servicios existentes conservan sus direcciones». No usar «Apagar router» o «Sin conexión» como sustitutos de este estado.

Una interfaz inactiva sigue visible con sus direcciones y redes. Impide nuevas asociaciones y reservas en sus redes vinculadas, pero conserva servicios, IP activas/reservadas y protección de IP locales. El selector de asociaciones nuevas no ofrece interfaces inactivas como destino elegible. Una asociación histórica inactiva se conserva al editar otro dato y aparece etiquetada; no se sustituye silenciosamente.

Si la interfaz cambia a inactiva mientras un borrador está abierto, el servidor rechaza la nueva asociación/reserva. La UI mantiene la entrada y ofrece revisar o activar con el permiso correspondiente; no desvincula la red para eludir la restricción. Las redes históricas sin interfaz continúan siguiendo el estado de router y red vigentes.

Durante cualquier guardado, deshabilitar doble envío y conservar la acción pendiente identificada. Actualizar estado y filas solo tras éxito. Un error mantiene el estado anterior y permite reintentar. Activar una interfaz vuelve a permitir operaciones elegibles; no crea redes, no reasigna IP ni modifica servicios existentes.

## 10. Identidad, responsive y accesibilidad

La solución compone tabla operativa, detalle y formularios del portal. Reutiliza `PortalPanel`, `PortalAlert`, `PortalEmptyState`, `PortalSkeletonBlock`, controles de `@iwana/ui` y el patrón de drawer existente. No añade una nueva biblioteca, tokens de marca o patrón visual; DS-OWNER debe documentar anatomía y estados antes de congelar su contrato.

Mantener como rasgos de firma funcionales la jerarquía y profundidad del panel existente y los datos técnicos monoespaciados/tabulares. La firma y los tokens se resuelven desde sus fuentes vigentes, sin definir valores nuevos aquí. El estado activo y la navegación no dependen solo del color.

| Ancho y tema          | Criterio observable                                                                                                                                                     |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 375 px, claro/oscuro  | Formulario en una columna; contexto de router, modo de entrada y errores disponibles sin desbordamiento horizontal de página. Tablas desplazan dentro de su contenedor. |
| 768 px, claro/oscuro  | Contexto y acciones persistentes; campos pueden agruparse sin alterar orden de lectura o perder ayudas.                                                                 |
| 1280 px, claro/oscuro | Tabla, filtros, estado y acciones escaneables; detalle agrupa interfaces/direcciones sin columnas variables por cada interfaz.                                          |

En los seis escenarios: contraste WCAG 2.2 AA; foco visible; campos con etiqueta persistente, ayuda y error enlazados; áreas de acción de al menos 44 × 44 px; operación íntegra por teclado. Selección de candidata anuncia interfaz, dirección y prefijo. Protecciones automáticas se presentan como información, no como entradas editables.

Al abrir el drawer, el foco entra en el contexto de la tarea; al cerrarlo vuelve al control de origen. «Guardar y añadir red» mueve el foco a la nueva tarea y anuncia que el router se guardó. Un error dirige al resumen o primer campo inválido sin borrar datos. Los anuncios de carga y guardado no repiten todo el contenido ni bloquean navegación no dependiente. ### 13.2 Recorrido router → red

**A. Alta de router** (drawer «Registrar router»)

- Obligatorios: nombre, dirección de administración y al menos un método de control. Opcionales: sede física, nodo comercial y notas.
- «Interfaz LAN» sale del alta. El alta no exige interfaces (§4.1). En edición, la referencia anterior se muestra como dato heredado (13.9, filas 6–7).
- Acciones: **«Guardar y añadir red»** (primaria) y **«Guardar router»** (secundaria), más «Cancelar». La primaria es la ruta crítica del PRD (§3: «registrar router y continuar a su primera red»).
- En edición solo aparece «Guardar cambios» (primaria). No aparece «Guardar y añadir red» en modo edición.
- Enter envía la acción primaria. Supuesto: confirmar en fe-platform.

**B. Tras «Guardar y añadir red»**

1. El router se crea una sola vez. Con éxito y con identificador del servidor, el drawer del router se cierra.
2. Se abre «Registrar red IPv4» con el router fijado: «Router: <nombre> · Activo», y el enlace «Ver router». No hay selector de router.
3. Anuncio en región `role="status"`: «Router guardado. Completa su red IPv4.»
4. Foco en el primer control de origen del bloque (13.4). Si no hay candidatas, en «Bloque IPv4 (CIDR)». Un router recién creado no tiene interfaces: el modo inicial es «Bloque y puerta de enlace», con el aviso «Este router aún no tiene interfaces registradas. Puedes ingresar el bloque y la puerta de enlace directamente».

**C. Fallos**

- Falla guardar el router: se mantiene el formulario del router y no se abre la red.
- El router queda guardado y falla la red: el drawer de red muestra «El router está guardado. Completa o reintenta el registro de la red.», conserva lo escrito y reintenta solo la red. Nunca vuelve a crear el router.
- Respuesta incierta o conexión perdida al guardar el router: «No pudimos confirmar el guardado. Revisa el catálogo antes de intentarlo de nuevo.» No se reenvía sin confirmación.
- «Cancelar» la red conserva el router. La red se retoma con «Añadir red» desde el detalle del router, cuya fila muestra «0 redes».

**D. Entradas alternativas**

- Detalle del router → «Añadir red»: router fijado.
- Catálogo de redes con filtro de router: router fijado por el filtro (`Ipv4NetworkCatalogClient.tsx:41`).
- Catálogo de redes sin filtro: selector «Router» con routers activos, elegido una vez. Sin routers activos: «No hay routers activos. Activa un router o registra uno nuevo.» con enlace al catálogo de routers.
- Cambiar de router exige cerrar y empezar de nuevo. Nunca se reasigna un borrador en silencio.
- Si el router se desactiva con el formulario abierto, el servidor rechaza la operación. Se conserva el borrador: «El router se desactivó mientras completabas la red. Tus datos siguen aquí.» Acciones: «Volver al router» y «Volver al catálogo». No se elige otro router.

**E. Nombre sugerido editable**

- Regla: con bloque e interfaz asociada, `<nombre de interfaz> · <CIDR>`; sin interfaz, `<CIDR>`; sin bloque, el campo queda vacío con el marcador «Se sugerirá al definir el bloque».
- Presentación: la sugerencia aparece escrita en el campo. La ayuda dice «Sugerido. Puedes cambiarlo».
- Al primer cambio manual, el campo pasa a «Editado por ti» y deja de recalcularse. Aparece «Restaurar sugerencia» (botón de texto, 44 px).
- Campo vacío al guardar: se envía sin nombre y el servidor aplica la regla del contrato. La confirmación muestra el nombre final.
- Máximo 120 caracteres: «El nombre puede tener hasta 120 caracteres.» (`Ipv4NetworkDrawer.tsx:105`).
- Renombrar una interfaz no cambia el nombre de la red ya guardada (§6.3).

**F. Orden del formulario de red** (decisión del autor): router (contexto) → origen del bloque → bloque → puerta de enlace → rango para servicios → protecciones y exclusiones → método por defecto → nombre → resumen. El nombre va después del bloque, porque depende de él. El orden actual de `Ipv4NetworkDrawer.tsx` pone el nombre primero.

### 13.4 Elección entre candidatas

- Las direcciones de la interfaz asociada se muestran como grupo de opciones «Dirección base de la red» (`fieldset` con `legend`). Cada opción: `<interfaz> · <IP con prefijo>` y su origen «Registrada en <interfaz>».

- Candidata /32: se muestra como «No define un bloque para los servicios». No puede ser base del bloque. Puede proponerse como puerta de enlace cuando el operador ingresa el bloque; la coherencia se valida (§6.2).

- Recalculo: al cambiar la elección se recalculan bloque y puerta solo si siguen siendo sugerencias. Si el operador editó alguno, se conservan y aparece «Revisa la puerta de enlace: ya no coincide con el bloque». No hay cambio automático.

- Mientras carga, esqueleto con forma de la lista de opciones. Si la carga supera ~300 ms, el esqueleto aparece (Firma §2.8).

### 13.5 Puerta de enlace confirmada

- Propuesta solo desde una IP explícita, con el mismo host: `192.0.2.1/24` → `192.0.2.1`; `192.0.2.254/24` → `192.0.2.254`. Nunca `.1` por defecto y nunca la IP de administración.
- Visible con su origen: «Propuesta desde bridge-clientes · 192.0.2.1/24». Cambiarla abre el campo y el valor pasa a «Editada por ti».
- Puerta virtual o distinta de la IP local: admitida si pertenece al bloque. El resumen dice «Distinta de la IP registrada en <interfaz> (<IP>). Confirmada por ti.»
- Pertenencia al bloque: validación en cliente como espejo de la regla del servidor (`network-catalog.service.ts:651-681`). El servidor es la autoridad.
- Confirmación: el resumen antes de «Guardar red» muestra bloque, puerta y su origen. Guardar es la confirmación; no hay modal adicional (§6.3).
- Después de guardar, el detalle muestra solo «Puerta de enlace confirmada: <IP>». Según HLD D-2, el origen no se persiste: aparece solo en el resumen previo al guardado (13.16 G).
- Inmutabilidad: editar una interfaz o una dirección no cambia la puerta ni el bloque. El detalle de red lo dice: «Cambiar la interfaz o su dirección no modifica esta puerta de enlace».
- Cambiar el host de una dirección usada como puerta: el servidor rechaza. Mensaje: «Esta dirección se usa como puerta de enlace de una red. Revisa su configuración antes de cambiarla.» Sin cascada ni desasociación.

### 13.6 Protecciones automáticas y exclusiones

Dos bloques separados, en el drawer de red y en el detalle de red.

- **Protegidas automáticamente** (solo lectura, sobre `iwana-surface-soft`, con texto e icono): dirección de red, difusión, puerta de enlace, e IP de interfaces registradas dentro del bloque (solo si `ipProtection` es `ACTIVE`; 13.16 F), incluidas las de otro router de la empresa o de una interfaz inactiva. Texto: «Estas direcciones no se asignan a servicios y no se editan aquí.» En el alta, red, difusión y puerta aparecen como «Vista previa; se confirma al guardar».
- **IP excluidas de asignación** (editable): área de texto, con valores separados por comas. Ayuda: «Opcional. Para equipos u otros usos. Hasta 256 direcciones del bloque.» Contador visible «3 de 256». Vacío: «Sin exclusiones adicionales». Es un estado, no un error, y no quita protecciones.
- Una IP protegida repetida en exclusiones: nota no bloqueante, «Ya está protegida automáticamente; no reduce la capacidad dos veces». Se deduplica antes de contar.
- Fuera del bloque: error del campo con la lista de direcciones afectadas: «Estas direcciones no pertenecen al bloque 192.0.2.0/24: <lista>. Quítalas o cambia el bloque.» El cliente valida la misma regla; el servidor decide (D1).
- Ocupada por un servicio (reservada o activa): «<IP> ya está reservada o activa en un servicio. Quítala de las exclusiones o revisa el servicio.» Requiere código propio (D1).
- Capacidad: solo en el detalle y tras guardar, con las cifras del servidor: total asignable, reservadas, activas y libres. Texto accesible: «12 de 240 direcciones ocupadas; 228 libres». En el alta se muestra «Se calculará al guardar». Decisión del autor: no hay previsualización de capacidad, para no publicar un segundo cálculo.

### 13.7 Estado del catálogo

- Router y red: badge «Activo» (variante success) o «Inactivo» (neutral), con texto y forma. El control dice «Desactivar» o «Activar» en texto visible, con nombre accesible «Desactivar router <nombre>».
- Ayuda visible en el detalle, bajo el estado, no solo como tooltip. Activo: «Activo en el catálogo.» La disponibilidad para reservas es otro dato y se muestra aparte (13.16 B). Inactivo: «No acepta nuevas reservas. Los servicios existentes conservan sus direcciones.» Al desactivar se muestra antes del control: «Desactivar impedirá nuevas reservas; los servicios existentes conservan sus direcciones».
- No pide confirmación: el cambio es reversible y no libera direcciones. El resultado se anuncia en la región de estado.
- Interfaz, sede y referencia histórica: «Activa» / «Inactiva» (concordancia con el sustantivo femenino). Router y red: «Activo» / «Inactivo». Decisión V4.
- Interfaz inactiva: no aparece como destino de nuevas asociaciones ni de reservas. Sus direcciones, redes y protecciones siguen visibles.
- Referencias históricas inactivas (sede, nodo, interfaz): visibles con nombre y etiqueta «Inactiva». No se sustituyen al editar otro dato.
- Lectura sin gestión: estado solo como texto, sin controles.
- Prohibido en la UI: «Apagado», «Encendido», «Sin conexión», «Online», «Apagar router».

### 13.8 Referencias de sede y nodo

- Tres acciones distintas: no tocar el selector (conserva); «Quitar asociación» (desasocia; botón secundario junto al selector, nombre accesible «Quitar asociación con <nombre>»); elegir otra activa (asigna, validada por el servidor).
- Hasta que el contrato publique `null` en runtime (API v1.2 §3.1; congelación en G4), el selector de edición no ofrece quitar la sede. La opción «Sin sede física asociada» aparece solo en el alta. Motivo: hoy la opción vacía omite la clave (`NetworkRouterDrawer.tsx:135-140`) y el servidor conserva la sede en silencio.
- Sede inactiva asociada: aparece con nombre y «Inactiva»; no se cambia hasta elegir una activa.
- Referencia ajena, inexistente o de otro router: «La referencia seleccionada no está disponible para esta operación. Actualiza la selección.» Nunca se muestra un nombre ajeno.
- Opciones: «<nombre> · <tipo de sede>», con las etiquetas de tipo que ya usa Organización. El dato `siteType` existe (`api-client.ts:4906-4916`).
- Nodo comercial: su ayuda, separada de la sede, conserva el significado de cobertura (`network-catalog-labels.ts:9-10`).

### 13.16 Decisiones incorporadas en v1.2–v1.4

**Origen.** Revisión G1 de la UX sobre el PRD y el HLD addendum y consolidación con la API v1.2 y el modelo v1.6. Esta sección prevalece sobre 13.1 a 13.15 cuando haya contradicción. No cierra G2.

**A. Referencia LAN anterior y conversión** (HLD D-3; modelo «Normalización confirmada»; API v1.2 §4.2 y §5)

- La fila del router muestra «Referencia LAN anterior: <texto>» en solo lectura, con la nota «Dato heredado. No es una interfaz registrada.». No se edita ni se borra. Si el detalle trae `legacyLanInterfaceId` (UUID), la fila muestra «Convertida en <nombre>» con enlace a la interfaz y «Convertir en interfaz» no aparece (HLD D-15; cierra la decisión de UX de O-API-14).
- «Convertir en interfaz» (solo con `network.catalog.manage`) abre un formulario de confirmación:
  - Nombre: precargado con el texto y editable. 1 a 64 caracteres tras recortar, único por router sin distinguir mayúsculas. Conflicto `INTERFACE_NAME_IN_USE`: «Ya existe una interfaz con ese nombre en este router. Usa otro nombre.».
  - Clase: obligatoria y sin preselección, porque no se infiere del texto. Opciones: «Física» (`PHYSICAL`), «Puente (bridge)» (`BRIDGE`), «VLAN» (`VLAN`) y «Otra» (`OTHER`).
  - Dirección con prefijo: opcional. Ayuda: «No se toma del texto anterior. Escríbela si la conoces.». Si se deja vacía, la interfaz nace sin direcciones (RF-IF-01).
  - Notas: opcionales, hasta 1000 caracteres.
- Resumen antes de confirmar: «Se creará la interfaz <nombre> (<clase>). El texto anterior no cambia. Las redes existentes seguirán sin interfaz; puedes asociarlas una a una.». Botón «Confirmar interfaz» (primario) y «Cancelar».
- Ruta: `POST /network/routers/:id/interfaces` con `convertLegacyLan: true` (HLD D-20). Es la única ruta de conversión. Crea la interfaz y fija `legacyLanInterfaceId` en la misma transacción. El cuerpo admite `name` (precargado y editable), `kind`, `notes` opcional y una dirección con prefijo opcional explícita (API v1.2 §5.2); nunca la deriva del texto anterior. Si se deja vacía, la interfaz nace sin direcciones. Si `ipProtection` está pendiente, la conversión sin dirección sigue disponible y el alta de la dirección se ofrece solo cuando la protección esté activa. La respuesta `201` incluye la interfaz, la dirección (si se envió) y el router actualizado. Errores propuestos: `LEGACY_LAN_NOT_AVAILABLE`, `LEGACY_LAN_ALREADY_CONVERTED`, `INTERFACE_NAME_IN_USE`, `ADDRESS_NOT_USABLE`, `IP_IN_USE` y `IP_PROTECTION_PENDING` para una dirección enviada con protección pendiente; se muestran con los mensajes de 13.9.
- Después de convertir, la interfaz aparece en el detalle del router. El texto anterior sigue visible y pasa a «Convertida en <nombre>» solo cuando el detalle trae `legacyLanInterfaceId`. Sin ese dato, la fila muestra solo el texto anterior. La UI no infiere la conversión por el nombre. API v1.2 declara `legacyLanInterfaceId` en `RouterDto` (§9); su publicación runtime queda en O2-C y no se presupone antes de G4.
- Las redes legadas no se asocian por la conversión. Se asocian una a una con «Asociar interfaz» (13.9 fila 6, CA-R08).
- Respuesta incierta o conflicto: 13.9 filas 24 y 25.

**B. Disponibilidad para reservas con motivo** (HLD D-11; API v1.2 §9)

- Son dos datos distintos. El estado de catálogo (Activo o Inactivo, 13.7) no indica si la red admite reservas. Un badge «Activo» con «Sin reservas nuevas» es un estado válido.
- El dato llega en `reservationAvailability`, con dos campos: `available` (booleano) y `reason`. Si `available` es `true`, `reason` es `null`. Si es `false`, `reason` trae `ROUTER_INACTIVE`, `NETWORK_INACTIVE` o `INTERFACE_INACTIVE`, según la precedencia del servidor (router, red, interfaz). La UI decide por `available` y muestra solo el texto del `reason` devuelto.
- Textos:
  - `ROUTER_INACTIVE`: «Sin reservas nuevas: el router está inactivo.» Ayuda: «Activa el router para volver a reservar en sus redes.».
  - `NETWORK_INACTIVE`: «Sin reservas nuevas: la red está inactiva.» Ayuda: «Activa la red para volver a reservar en ella.».
  - `INTERFACE_INACTIVE`: «Sin reservas nuevas: la interfaz <nombre> está inactiva.» Ayuda: «Los servicios existentes y las direcciones protegidas se conservan. Activa la interfaz para volver a reservar.».
  - Disponible: «Disponible para reservas.» Ayuda: «No indica cuántas direcciones quedan libres. Revisa la ocupación.».
- Detalle de interfaz inactiva: «Inactiva. No admite nuevas reservas en sus <N> redes vinculadas. Sus direcciones siguen protegidas.». `<N>` viene de `networkCount` (API v1.2 §5).
- Activar una interfaz: antes de confirmar, «Sus redes volverán a reservar solo si su router y su red también están activos.» (modelo §6).
- Flujo de reserva (spec 2026-10-22 §6): una red sin reservas aparece deshabilitada con su motivo, no oculta. El manejo de pausa y `409 RESERVATIONS_PAUSED` está en la spec de aprovisionamiento v1.3 §6.
- Nombre del campo: `available`, según HLD D-19 y API v1.2 §9. La respuesta usa `reason: null` cuando está disponible; nunca `eligible` ni `AVAILABLE`. La forma está propuesta en API v1.2 y solo queda publicada/congelada en runtime tras O2-C y G4.

**C. Corregir dirección** (HLD §5.6 y D-1/D-24; API v1.2 §4.2 y §6; modelo v1.6 §6)

- Acción «Corregir dirección» en cada fila de dirección (44 px). Es distinta de renombrar la interfaz, que no muestra campos de dirección.
- Visible con `network.catalog.manage`. Si la interfaz está inactiva (guarda c), la acción aparece deshabilitada con «Activa la interfaz para corregir sus direcciones.». Si el servidor responde `INTERFACE_NOT_AVAILABLE`, se muestra el mismo texto.
- Formulario:
  - «Dirección actual» en solo lectura, con fuente monoespaciada.
  - «Nueva dirección con prefijo», editable.
  - «Motivo del cambio»: lista cerrada y obligatoria, sin texto libre (HLD D-16). Opciones: «Error de registro», «Cambio de equipo» y «Reasignación planificada». Ninguna viene preseleccionada. Ayuda: «Queda registrado en el historial de cambios.».
- Resumen antes de confirmar, con el valor actual y el nuevo:
  - «Dirección: <actual> → <nueva>.».
  - «Redes vinculadas: <N>. No cambian sus bloques, puertas de enlace ni asignaciones.» (guarda g).
  - Si solo cambia el prefijo: «Revisa si el bloque de cada red vinculada sigue siendo coherente. El sistema no lo cambia.» (API v1.2 §6).
  - Si cambia el host IPv4, efecto sobre la IP anterior (HLD D-17/D-24): «La IP <anterior> dejará de estar protegida y podrá asignarse a un servicio.». Ayuda: «Solo si está dentro del rango asignable de una red.». Este efecto y su confirmación solo se muestran cuando cambia el host, no cuando cambia únicamente el prefijo.
- Confirmación del host liberado (HLD D-17/D-24; API v1.2 §6): compara el host IPv4, ignorando el prefijo. Solo si cambia el host, el resumen dice «La IP <anterior> dejará de estar protegida y podrá asignarse a un servicio.» y muestra la casilla «Entiendo que la IP <anterior> dejará de estar protegida.». «Confirmar corrección» (primario) permanece `aria-disabled` hasta marcarla y conserva la ayuda «Marca la casilla para confirmar el efecto.» (patrón de 13.4). Al enviar, la petición incluye `confirmReleasedHost: true`. Si la casilla no está marcada, no se envía la petición. Si el servidor responde `400 ADDRESS_RELEASE_CONFIRMATION_REQUIRED` porque falta el campo o es `false`, no se anuncia éxito, no se cambia la dirección ni su versión y se conserva el borrador con «Confirma que la IP anterior dejará de estar protegida antes de guardar.». No se exige modal adicional; «Cancelar» siempre está disponible.
- Si solo cambia el prefijo, no se muestra la advertencia de liberación ni la casilla, y se omite `confirmReleasedHost`. La respuesta exitosa contiene `releasedHost: null`; la UI informa el cambio de prefijo y la revisión de redes vinculadas descrita arriba, sin sugerir que se liberó una IP. La UI no anuncia éxito antes de recibir respuesta exitosa ni deduce `releasedHost` de la entrada local.
- Textos de guardas:
  - (a) El host anterior es puerta de enlace (`INTERFACE_ADDRESS_IS_GATEWAY`): «Esta dirección se usa como puerta de enlace de una red. Revisa su configuración antes de cambiarla.». No hay cascada (13.5).
  - (b) Host anterior o nuevo con asignación viva (`IP_IN_USE`). Si es el anterior: «Esta dirección tiene un servicio reservado o activo, así que no puede corregirse. Revisa el servicio antes de cambiarla.». Si es el nuevo, aplica el texto de 13.9 fila 20.
  - (c) Interfaz inactiva (`INTERFACE_NOT_AVAILABLE`): texto de arriba.
  - (d) Dirección utilizable (HLD D-12; API v1.2 §5): para prefijos /1 a /30, la dirección no puede ser la de red ni la de difusión; /31 y /32 se admiten. Texto: «La nueva dirección no es utilizable en este prefijo. Elige otra.». Duplicado en la misma interfaz (`INTERFACE_ADDRESS_DUPLICATED`): «Esta interfaz ya tiene esa dirección.». Código `ADDRESS_NOT_USABLE` (HLD D-18): mensaje de campo, no un `VALIDATION_ERROR` genérico.
  - (g) Texto del resumen, arriba.
- Errores de versión: 13.9 fila 24.

**D. Desasociar interfaz** (HLD D-13; API v1.2 §8: `interfaceId: null` en PATCH de red)

- En el detalle de red: «Quitar interfaz» (botón secundario, 44 px), visible con `network.catalog.manage` cuando la red tiene interfaz.
- Resumen antes de confirmar:
  - Interfaz activa: «La red quedará sin interfaz asociada y seguirá con las reglas de router y red. La interfaz no se borra.».
  - Interfaz inactiva: «La interfaz <nombre> está inactiva. Si quitas la asociación, esta red volverá a poder reservar si su router y su red también están activos.». Se presenta como advertencia, con texto y forma, no con lima.
- Confirmación con el botón «Quitar interfaz». El CIDR y la puerta de enlace no cambian (API v1.2 §8). La red queda en «Sin interfaz asociada» (13.9 fila 6).

**E. Referencias de sede y nodo** (API v1.2 §3.1; HLD §5.5)

- Valor nuevo con sede o nodo inactivo (`SITE_OR_NODE_INACTIVE`, API v1.2 §3.1; distinto de `CATALOG_REFERENCE_INACTIVE`, que es para router o red):
  - Sede: «La sede <nombre> está inactiva. Elige una sede activa o mantén la actual.».
  - Nodo comercial: «El nodo comercial <nombre> está inactivo. Elige un nodo activo o mantén el actual.».
  - Si el nombre no está disponible: «La sede seleccionada está inactiva. Elige otra.» (o «El nodo seleccionado…»).
- Valor igual al guardado: se guarda sin validar y no bloquea otras ediciones (13.8).
- `null` («Quitar asociación»): «La sede deja de estar asociada al router. La sede no se borra.». Mismo texto para el nodo. Sin confirmación adicional, porque no afecta reservas.
- Referencia ajena o inexistente (`RESOURCE_NOT_FOUND`): 13.9 fila 22. El texto final se valida en O-API-12.

**F. Captura de direcciones bloqueada** (HLD D-7 y §5.2; API v1.2 §§9.1–10; O-API-6)

- Si `ipProtection` es `PENDING` (HLD D-14), la UI muestra: «Todavía no puedes registrar direcciones en esta interfaz. Puedes crear la red con bloque y puerta de enlace.». Es captura bloqueada por versión, no un fallo temporal: por eso no dice «inténtalo más tarde».
- Si no se puede leer `CatalogMetaDto` con autorización o falta `ipProtection`, la UI no ofrece alta ni corrección de direcciones y muestra: «No pudimos comprobar si es posible registrar direcciones. Reintenta antes de continuar». No muestra `ACTIVE` ni `PENDING`, y no los infiere a partir de una respuesta parcial o datos previos.
- Quedan ocultos «Añadir dirección» y «Corregir dirección». Ambas son escrituras de direcciones (D-7). La interfaz y sus redes siguen usables. El alta de red en modo bloque y puerta sigue disponible (13.4).
- «Protegidas automáticamente»: red, difusión y puerta de enlace se muestran siempre. La fila de IP locales se muestra solo si `ipProtection` es `ACTIVE`. Con `PENDING`, el bloque no dice nada sobre IP locales. La UI nunca afirma «no hay IP locales protegidas».
- Metadatos (HLD D-14; API v1.2 §9.1): `GET /network/catalog-meta` devuelve solo `ipProtection` con `network.catalog.read`; `GET /network/provisioning/meta` devuelve solo `reservationsPaused` con `network.provisioning.read`. La UI no los infiere. `ipProtection` pasa a `ACTIVE` solo tras la verificación de CA-R12 (O3). El contrato sigue siendo documental hasta O2-C/G4; los valores operativos los fija el servidor.
- Pausa de reservas: con metadato autorizado `reservationsPaused = true`, mostrar «Las reservas están pausadas temporalmente. Inténtalo más tarde.» y deshabilitar las acciones de reserva, replay que reemitiría una instrucción y regularización. Es el único caso en que «Inténtalo más tarde» es correcto; no es un motivo de `reservationAvailability` (13.16 B). El consumidor que no tenga `network.provisioning.read` no consulta ni infiere la pausa: si el servidor rechaza una de esas operaciones con `409 RESERVATIONS_PAUSED`, mostrar el mismo copy, conservar la OT y la entrada, y no anunciar éxito. El copy y el manejo se trasladan a la [spec de aprovisionamiento v1.3 §6](2026-10-22-mod13-aprovisionamiento-ux.md#pausa-temporal-de-reservas-y-regularizaciones).
- Si hay direcciones registradas y `ipProtection` es `PENDING`, se listan en solo lectura sin afirmar protección y sin acciones de captura.
- El texto no dice «inténtalo más tarde»: el bloqueo depende de la versión, no de un fallo temporal.
- Rollback (HLD D-7): la UI no puede compensar una API antigua que ignore direcciones locales. La reversión solo procede según la conciliación y la compatibilidad definidas allí; mientras exista riesgo de asignación, el backend mantiene protección compatible o detiene reservas nuevas y declara `reservationsPaused`. La UI muestra la pausa a partir del metadato autorizado o del `409 RESERVATIONS_PAUSED`, pero no sustituye el control del servidor.

**G. Origen de la puerta de enlace** (HLD D-2)

- Antes de guardar: «Propuesta desde <interfaz> · <IP con prefijo>» o «Editada por ti» (13.5).
- Después de guardar, el detalle muestra solo «Puerta de enlace confirmada: <IP>». El origen no se persiste y no se muestra. La auditoría lo registra (HLD D-2).
- Cierra la pregunta D4 de 13.14 (O-API-7).

La captura/corrección de IP locales permanece fail-closed hasta CA-R12 y protección completa: solo se habilita cuando el servidor devuelve metadatos autorizados con `ipProtection: ACTIVE`, estado que no puede fijarse antes de esa evidencia. Ante metadatos ausentes, parciales, no autorizados o `PENDING`, la UI no anuncia estado ni ofrece captura/corrección.
- Tras capturar IP locales, una reversión no puede dejar activo un backend que ignore esas filas. Se conserva una versión que aplique la protección o se detienen, con control compatible y verificado, reserva, replay que reemite instrucciones y regularización hasta conciliar; un indicador de pausa en UI no sustituye esa protección del servidor (ADR-101 v1.1, API v1.2 §12).

**D3 — selector de sede física con paginación remota.** La API v1.6 (forma funcional revisada en v1.5) documenta `GET /network/router-site-options`, con el permiso existente `network.catalog.manage`, `page`/`limit` y metadatos de paginación. Evita depender de `ORGANIZATION_SITES_READ` en `GET /organization/sites` y no amplía permisos globales. La ruta resuelve las opciones por el puerto tipado de Organización y filtra server-side las sedes autorizadas antes de contar y paginar, conforme a D-23. El selector recorre más allá de la primera página; muestra el nombre y el tipo visible de cada sede física según el catálogo de Organización, e indica cuando una asociación existente está inactiva. La sede elegida se conserva al cambiar de página. La búsqueda global no forma parte del cierre D3. La paginación remota satisface el criterio de acceso al catálogo sin inventar una búsqueda local ni cargar todo el catálogo en memoria. FE v1.2 confirmó factibilidad; la ruta y su response siguen sin publicarse en runtime ni congelarse. Las pruebas de permisos efectivos y la publicación/freeze corresponden a O2-C/O2-H/G4.

**D7 — pausa y metadatos autorizados.** SEC-ENG v1.4 da PASS de diseño al uso del `409 RESERVATIONS_PAUSED` como respuesta autoritativa cuando la persona no tiene permiso para leer `reservationsPaused`; la interfaz no infiere la pausa ni depende de metadatos no autorizados. La interfaz muestra `ipProtection` únicamente cuando recibe el metadato completo por una respuesta autorizada y no usa ese estado como control de seguridad. Quedan pendientes de runtime la comprobación de permisos efectivos, la publicación de contratos y evidencia de que los consumidores de reserva/regularización respetan el 409 sin filtrar datos. No se muestra `ipProtection: ACTIVE` ni se ofrece captura o corrección de direcciones locales hasta que CA-R12 pruebe reserva manual, reserva automática y ocupación, y exista evidencia de rollout/rollback compatible con ADR-101.

**D9 — candidatas y errores de grupo accesibles.** La composición usa `RadioCardGroup` con inputs de radio nativos, etiquetas visibles y estados de carga, error, selección y ausencia de candidatas. El error y su ayuda deben asociarse programáticamente al grupo mediante `aria-describedby`/`aria-invalid`, además de presentarse en texto; no basta el color. FE v1.2 confirma factibilidad y SR-QA v1.3 recomienda PASS de testabilidad/diseño. AI-EM-ARCH cerró G2 tras la revisión independiente UX/DS y la suite contractual registrada por QA; la implementación integrada sigue pendiente de O2-FE/O3.

**D10 — detalle de router en URL.** Un `routerId` en la query abre el side peek directamente, permite recargar/compartir el estado, conserva filtros y página de la lista y mantiene navegación del historial: abrir desde fila añade el detalle, Atrás lo cierra y el botón de cierre retira solo `routerId`. Al abrir desde una URL directa, si la fila de origen ya no está disponible, el foco vuelve al encabezado de la lista. El panel no muestra nombre ni datos del router hasta que una lectura por ID sea autorizada.

El dictamen O1-F observó que entonces no existían `GET /network/routers/:id` ni `networkApi.getRouter(id)` en runtime. La API v1.6 (forma funcional revisada en v1.5) documenta la lectura por ID, autorización D-23 sobre la sede persistida, proyección permitida después de autorizar y 404 uniforme para ID inexistente o fuera de scope. FE v1.2 confirmó suficiencia de los resúmenes legibles; SEC v1.4 y QA v1.3 revisaron la forma de diseño, con PASS y PASS recomendado respectivamente. G3 está cerrado formalmente. **D13 — referencias, errores y privacidad.** SEC-ENG v1.4 da PASS de diseño al mapeo D-23–D-25: 404 genérico e idéntico para referencia inexistente, relación padre incorrecta o recurso fuera de scope; 403 solo para falta de permiso de acción dentro del scope autorizado; 422 genérico para destino accesible pero inactivo; 409 para pausa o conflicto real. La interfaz no identifica cuál causa produjo un 404 ni presenta nombre, ubicación, router, interfaz o dirección vecina de otro recurso. El motivo tipado `IP_PROTECTED_BY_INFRASTRUCTURE` puede distinguirse de una IP ocupada por servicio siempre que la respuesta no revele la ubicación de la protección. La integración runtime, las pruebas de autorización/no enumeración y la verificación de los consumidores siguen pendientes.
