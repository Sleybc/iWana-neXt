# Adenda contractual C-API-1 v1.1 — búsqueda de suscriptores

**Fecha:** 2026-10-12  
**Estado:** Adenda autorizada por decisión del usuario durante Ola 1-bis. C-API-1 v1.0 permanece inalterado.  
**Consumidores:** API MOD05 (`sr-backend`) y portal (`fe-platform`).

## 1. Motivo y compatibilidad

C-API-1 v1.0 define `POST /crm/subscribers/search` con criterios exactos `documentNumber`, `nit`, `email` y `phone`, y exige al menos uno. Esta adenda añade búsqueda libre por POST para que el listado/typeahead no envíe nombres u otros valores personales en la URL. No sustituye ni elimina los criterios exactos de v1.0. `GET /crm/subscribers/search` queda retirado y responde 404.

## 2. Request

`POST /crm/subscribers/search`

El JSON body acepta los campos congelados de C-API-1 v1.0 y añade `search`:

```ts
{
  documentNumber?: string;
  nit?: string;
  email?: string;
  phone?: string;
  search?: string; // búsqueda libre para listado/typeahead
}
```

Debe estar presente al menos uno entre `documentNumber`, `nit`, `email`, `phone` y `search`. No se aceptan campos de filtros o paginación en el body.

La búsqueda libre es literal: `%`, `_` y `\\` que aparezcan en la entrada se escapan como caracteres ordinarios antes de construir el patrón `ILIKE`; solo los `%` agregados por el servidor alrededor del valor son comodines. La consulta parametriza el patrón y declara el carácter de escape explícitamente en SQL. No se concatena entrada del usuario en SQL.

Los criterios exactos y `search` no se pueden combinar en la misma petición: el servidor valida esa exclusión para evitar semánticas ambiguas.

## 3. Query no personal para listado y paginación

Cuando el body contiene `search` (listado/typeahead), el POST puede recibir los parámetros no personales que ya acepta el listado: `status`, `personType`, `customerSegment`, `stratum`, `page`, `limit`, `sortBy` y `sortDir`. Se conservan las reglas y techos vigentes del listado (incluido `limit` máximo 100). En lookup exacto no se aceptan filtros ni paginación en query. Ningún identificador personal ni `search` puede viajar en la query.

`GET /crm/subscribers` conserva estos mismos filtros y paginación no personales. Se retira `@Query('search')`; la búsqueda libre de la lista debe usar el body del POST.

## 4. Response

La búsqueda libre sirve la proyección de listado definida por C-API-2 v1.1 y conserva el envelope de paginación:

```ts
{
  data: SubscriberListItem[];
  total: number;
  meta: ListMeta;
}
```

La búsqueda exacta por criterios de C-API-1 v1.0 conserva `{ data: SubscriberListItem[] }`; el servidor puede adjuntar `total` y `meta` solo si el consumidor del listado los necesita, sin alterar los campos de cada elemento.

## 5. Acceso y auditoría

POST y GET listado quedan limitados a `ADMIN`, `NOC`, `SALES`, `SUPPORT` y `ACCOUNTANT`, de acuerdo con C-API-2 v1.1 §6. El API proyecta cada fila mediante `SubscriberListItem` y el mapa ratificado de campos por rol. En POST y GET, `LIST_ACCESS` se espera (`await`) y registra únicamente rol, dimensión/criterio aplicado como marcador (`"(aplicado)"`), filtros no personales y dimensiones de paginación. No registra body, query personal, texto de búsqueda, valores encontrados ni filas devueltas.

## 6. Migración del consumidor

- `subscribersApi.search(criteria)` conserva el POST exacto definido en v1.0.
- `subscribersApi.list({ search, ...nonPersonalFilters })` usa POST `/crm/subscribers/search`, coloca solo `search` en el body y coloca filtros/paginación no personales en query.
- `subscribersApi.list({ ...nonPersonalFilters })` sin `search` puede continuar usando GET `/crm/subscribers`.
- Ningún consumidor construye URL/query con documento, NIT, correo, teléfono ni texto de búsqueda libre.
