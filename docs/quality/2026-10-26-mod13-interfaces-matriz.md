- **Prueba discriminante:** si la segunda etapa falla (ruta `POST /network/ipv4-networks` interceptada con error) y luego se reintenta, el número de `POST /network/routers` observados debe ser 1 (UX §4.1, `docs/specs/2026-10-26-mod13-interfaces-ux.md:60`; API §6.4, `docs/specs/2026-10-26-mod13-interfaces-api.md:154`). Si la UI pide otra vez el router o lo recrea, falla. Si la sugerencia de nombre sobrescribe un nombre escrito por el operador, falla.
- **Fixture:** router sintético creado en el seed; error simulado con `page.route` siguiendo los helpers de `e2e/tests/helpers/`. Selectores por rol o etiqueta (`playwright-skill/SKILL.md:61-68`).
- **Evidencia:** conteo de peticiones por método y ruta; la URL conserva filtro y página; sin `waitForTimeout` (`e2e-testing-patterns/SKILL.md:189`).

### CA-R03 — Derivación de bloque y gateway

- **Prueba discriminante:** `192.0.2.254/24` debe proponer bloque `192.0.2.0/24` y gateway `192.0.2.254`, no `.1` (UX §6.2, `ux.md:112`). Un `/32` no debe generar pool (UX `:114`; API §6.2 `api.md:138`, código `NETWORK_PREFIX_NOT_ASSIGNABLE`). Con dos candidatas, guardar sin elegir debe quedar bloqueado (UX `:110`; API `:137`). Si el sistema elige la primera sin petición, falla.
- **Fixture:** `192.0.2.1/24`, `192.0.2.254/24`, `192.0.2.7/32`, y dos candidatas `198.51.100.1/24` y `198.51.100.9/24`.
- **Evidencia:** unitarias y de componente con 0 `skipped`; validación de API en unitaria sobre el contrato.

### CA-R04 — Gateway manual o virtual estable

- **Prueba discriminante:** renombrar la interfaz o cambiar un prefijo no modifica `ipv4_networks.cidr` ni `gateway`, ni la versión de la red; ningún camino actualiza el gateway confirmado en cascada. Según HLD D-24 y API v1.5 §6, si `correct` cambia el host, únicamente `confirmReleasedHost: true` permite continuar. Con campo ausente o `false`, el servidor devuelve `400 ADDRESS_RELEASE_CONFIRMATION_REQUIRED`; comparar snapshot de dirección, versión y auditoría antes/después: los tres permanecen iguales. La UI no envía la solicitud si la casilla no está marcada; si recibe el 400, conserva borrador/dirección y anuncia que el cambio no se completó. Con `true`, se verifican guardas, auditoría y que el host anterior queda liberado. Si cambia solo el prefijo, no se exige confirmación, se omite el campo, la respuesta tiene `releasedHost: null`, el host continúa protegido y no se alteran red, gateway ni asignaciones. Un cambio de host/prefijo no elude las demás guardas HLD §5.6.
- **Fixture:** red 192.0.2.0/24 con gateway manual `192.0.2.250`; interfaz con 192.0.2.1/24. La IP física y el gateway virtual son distintos a propósito.
- **Evidencia:** snapshot HTTP/PostgreSQL de dirección, versión, redes, gateways, asignaciones y auditoría; request interceptada en E2E para confirmar que el checkbox solo aparece ante cambio de host, el request contiene `true` únicamente entonces, y el 400 conserva estado y borrador. Los casos siguen pendientes de implementación y contrato runtime publicado/congelado G4; la captura permanece bloqueada con `ipProtection=PENDING` hasta CA-R12.

### CA-R05 — No asignables y ocupación deduplicada

- **Prueba discriminante:** una IP local del mismo tenant (de otro router) no puede asignarse en reserva automática ni manual. El conteo de ocupación no debe restar dos veces una IP que es gateway y local a la vez.
- **Fixture y cifras esperadas:** red 192.0.2.0/24, asignable 192.0.2.0 a 192.0.2.255, gateway `.1`, exclusión `.2`, IP local `.7` de otro router, e IP local `.1` que coincide con el gateway. El total esperado es **251** (256 − red − difusión − `.1` − `.2` − `.7`). Si `.1` se contara dos veces, daría 250 y fallaría. La fórmula sigue el caso existente (`ipam.service.postgres.integration.spec.ts:144-162`, que da 252 sin la IP local).
- **Prueba de rutas:** la protección debe estar en las tres rutas (`validateRequestedIp`, `findNextAvailableIp`, `readOccupancy`). Quitarla en una sola debe hacer fallar al menos un caso. Esto es una mutación controlada, no una prueba de producción.
- **Evidencia:** PostgreSQL real sobre schema con migraciones reales; cifras exactas en `total`, `reserved`, `active` y `free`.

### CA-R06 — Concurrencia de IP local frente a reserva, catálogo y escrituras IPAM

- **Prueba discriminante:** se ejecutan ambos órdenes de cada carrera en la sección 6; un resultado serializado válido, máximo una asignación viva por host y ningún `40P01`. Reservas automáticas, manuales, replay y regularización ven el mismo conjunto protegido.
- **Fixture:** red 192.0.2.0/24; IP candidata `192.0.2.50`.
- **Evidencia:** para cada par, dos órdenes; lock esperado observable en `pg_locks` o `pg_stat_activity`; ningún `40P01`; como máximo una fila `RESERVED`/`ACTIVE` por IP (índice `uq_ip_assignments_live`). Repetir 20 reservas concurrentes de IP distintas sobre schema creado con migraciones reales.

### CA-R07 — Referencias, IDOR, tenancy y alcance de sede

- **Prueba discriminante (D-23):** `POST /network/routers` con `organizationSiteId` pasa primero por el puerto de Organización para validar que el destino existe, pertenece al tenant y está activo; luego el puerto de Access Control autoriza esa sede. Un destino autorizado con `network.catalog.manage` crea; sede inexistente y sede existente fuera del scope tienen la misma respuesta 404 y no escriben. Sin sede destino se exige grant tenant-wide. En scope autorizado, la falta de `network.catalog.manage` da 403. `siteId`/`organizationSiteId` falsificados en body/query nunca amplían el alcance.
- **Prueba discriminante (D-22/D-23/D-25):** el mismo 404 `RESOURCE_NOT_FOUND` (status y cuerpo, sin detalles) se obtiene para ID inexistente/ajeno bajo JWT válido del tenant, referencia con padre/router incorrecto y recurso fuera del scope de sede. En `reserve` y `regularize` se aplica también a referencias inexistentes/ajenas o fuera de scope y relaciones de router incorrectas. Un recurso válido, accesible y activo dentro del scope, pero sin permiso de acción, da 403; router/red accesible pero inactivo conserva 422 `PROVISIONING_ORDER_NOT_ELIGIBLE`; pausa o conflicto de estado real da 409. `NETWORK_NOT_IN_ROUTER` no se devuelve en el caso de padre incorrecto. En updates, `null` desasocia, omisión conserva y UUID válido asigna.

- **Evidencia:** HTTP con PostgreSQL real y adaptadores de port controlados; igualdad exacta status/body para 404 por inexistente, padre incorrecto y fuera de scope; alta de sede con validación Organization→Access Control; 403 para falta de acción dentro del scope o falta de grant tenant-wide en alta sin sede; 422 `PROVISIONING_ORDER_NOT_ELIGIBLE` para destino accesible inactivo y 409 para pausa/conflictos. En UI, confirmar copy exacto de 404/403/422 según UX v2.1 §13.20 y aprovisionamiento UX v1.3 §9. No hay mutaciones/instrucciones en rechazos; el filtro no cuenta ni pagina recursos fuera de sede.

## 6. Diseño de carreras sin sleeps (CA-R06, CA-R05, REG-01)

Las carreras corren con conexiones PostgreSQL separadas y esquema aislado creado con migraciones reales. No se usan pausas fijas ni fixtures de tablas simplificadas.
Cada par de operaciones mutables se ejecuta en ambos órdenes, alternando cuál obtiene primero el lock; los casos H-7/H-8 son rechazos de validación y no carreras.

1. La primera transacción retiene el advisory/row lock del punto que se prueba.
2. Se lanza la operación rival en otra conexión.
3. La prueba espera por condición observable acotada: `pg_stat_activity`/`pg_locks` muestra la espera de lock, o una barrera del repositorio confirma el punto. El timeout falla el test; nunca se sustituye por `waitForTimeout`/sleep.
4. Se libera la transacción y se comprueba status, filas, versiones, instrucciones externas y la conciliación I-1.

| Hallazgo del modelo | Carrera/prueba discriminante requerida                                                                                                                                                                                                                                                                                      |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| H-1, H-10           | Reserva nueva vs desactivar router/red/interfaz. Si reserva gana, conserva asignación y desactivación espera; si desactivación gana, la reserva se rechaza. Router toma L0 y todos sus pools en orden UUID.                                                                                                                 |
| H-2, H-6            | Reserva vs PATCH de red; verificar ambos órdenes. El pool L2 se obtiene antes de insertar `service_provisionings`; PATCH hace L0→L2→fila. Ningún `40P01`; no debe existir fila de servicio mientras la reserva está esperando L2.                                                                                           |
| H-3, H-11           | Alta de red vs alta/corrección de IP local e inactivación de router. El alta toma L0, valida router `ACTIVE` con `FOR SHARE` y no inserta contra un router ya inactivo.                                                                                                                                                     |
| H-4, H-12           | Desactivar router/red/interfaz y asociar/desasociar interfaz↔red vs reserva, en ambos órdenes. L0→L2 de pools afectados→L3; referencias se revalidan bajo locks, no solo antes de abrir la transacción.                                                                                                                     |
| H-5                 | Probar por pares, en ambos órdenes, reserva/liberación/certificación/regularización y consumidor/reconciliador que escriben `ip_assignments`: L1 uniforme por OT y L2 en cada escritura; una carrera no pierde ni duplica estado de asignación.                                                                             |
| H-7                 | Exclusión fuera del CIDR y cardinalidad inválida no cambian fila/versión; CA-R09 verifica el rechazo, no se trata como deadlock test.                                                                                                                                                                                       |
| H-8                 | Validar sede/nodo por sus puertos y distinguir omisión/null/asignación en PATCH; CA-R07/MT-04 comprueban autorización sobre el recurso real, sin acceso cruzado a tablas.                                                                                                                                                   |
| H-9                 | Replay idempotente vs inactivación de router/interfaz/red, ambos órdenes. Replay conserva idempotencia pero no reemite instrucción cuando el destino ya no es elegible; la asignación viva no se elimina.                                                                                                                   |
| I-1                 | Alta/corrección de IP local ↔ reserva manual y automática, ambos órdenes. I-1 debe ser cero. |
| CA-R06              | Alta/corrección IP local ↔ alta de pool, ambos órdenes. La operación que llega segunda revalida bajo L0/L2; no hay doble asignación ni pool que ignore la protección.                                                                                                                                                       |

Mantener además las 20 reservas concurrentes distintas de REG-01 sobre esquema creado por migraciones reales. Ningún par da `40P01`; la unicidad parcial de `ip_assignments` se verifica al final, no se usa como sustituto del orden de locks.

**Consistencia concurrente por sede/nodo (CA-R07, O2-H).** PRD addendum §5, HLD §5.5 y UX CA-R07 requieren que una asociación nueva se valide activa, pero no ordenan estado activo al commit ni autorizan compartir la transacción/lock de Organización/Tenant. 1. **Desactivación antes de `findReference`:** el dueño confirma `isActive=false`; la lectura devuelve inactivo; creación/reasignación responde `409 SITE_OR_NODE_INACTIVE`; router/referencia/auditoría no se escriben.
2. **Desactivación después de lectura activa:** `findReference` lee activo y detiene Network en una barrera; el dueño confirma desactivación; se libera Network y la asociación puede completar. Verificar vínculo persistido y referencia ya inactiva/histórica al final. No esperar rechazo, revalidación bajo lock MOD13 ni `active=true` al commit.

Así se mantiene CA-R07 sin ampliarlo: al validar la asociación nueva el destino estaba activo; luego se preserva como referencia histórica, igual que PRD/UX permiten. ### 13.18 Fallos del Portal completo: causa en MOD13 y corrección (2026-10-27)

**Corrección de atribución.** Este documento, el plan y el informe registraron como «ajenos a MOD13» tres suites rojas del Portal completo: `mod05-deuda-fiscal-ui.portal`, `PlanCatalogFormPeek` y `RadioCardGroup.contract`. Las tres fallaban en la misma consulta, `getByRole('group', { name })`. La causa era el `role="radiogroup"` que la implementación MOD13 añadió sin commitear al `fieldset` de `RadioCardGroup` en `@iwana/ui`. Con ese rol, el `fieldset` pierde su `group` implícito. Viola la regla 5 del [contrato del componente](../specs/2026-10-11-ui-radio-card-group-contrato-componente.md) («No se agrega role=radiogroup ni role=radio»), y D9 solo autorizaba las props `aria-describedby` y `aria-invalid`.

**Veredicto AI-DS-OWNER (2026-10-27): opción A.** Se retira el rol y se conservan las dos props. `aria-invalid` es un refuerzo: solo se emite cuando es `true`, y el error vive en texto enlazado por `aria-describedby` y en el resumen `role="alert"` del consumidor. axe-core 4.11.1 trata `aria-invalid` como global. El contrato pasa a v1.1. No requiere ADR.
