## E2E contra API real — ejecución y bloqueo

Las credenciales se leyeron desde `.env.development.local` sin imprimirlas. Se configuró una cuenta de prueba y se creó un tenant activo desechable, con texto legal vigente y plan sintéticos. Cada escenario crea un expediente con identidad, contacto y dirección ficticios (`example.invalid`), registra el medio por el portal, dispara la conversión real y, cuando aplica, crea un contrato residencial de prueba. No se usaron `page.route()` ni datos de clientes reales.

| Escenario                                                                        | Resultado observado                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| -------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Radicar CONSULTA → verificar identidad → completar → resolver                    | **Pasa.** Solicitud, fechas y transiciones se guardan por los endpoints reales.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| Capturar autorización en expediente → convertir → mostrar el medio en ficha 360° | **Parcial / falla de producto.** La captura del expediente y la conversión pasan; la prueba confirma que `GET /crm/subscribers/:id/360` devuelve una autorización con `channel: TELEFONO`, pero la pestaña muestra “No hay una persona vinculada” y no muestra el medio. El endpoint serializa el suscriptor con `sanitizeResponse()` en `apps/api/src/modules/crm/subscribers/subscribers.controller.ts:512`, que no incluye `partyId`; `apps/portal/src/components/crm/subscribers/SubscriberDetailClient.tsx:354` usa `subscriber.partyId` para renderizar Cumplimiento. |
| Suplantación desde ficha 360° → suspensión del contrato impugnado                | **Bloqueado por el mismo defecto.** La prueba crea de forma independiente el expediente, la autorización, la conversión y el contrato sintético; al abrir Cumplimiento, no encuentra el botón “Radicar solicitud” porque `CompliancePanel` recibe `partyId` vacío. No se alcanzó a enviar la solicitud ni a suspender el contrato.                                                                                                                                                                                                                                          |

La cuenta de prueba completó su cambio obligatorio de contraseña por el formulario del portal; la nueva credencial permanece solo en `.env.development.local`, ignorado por Git. Se conserva el tenant sintético para reproducibilidad y revisión; todos los registros creados son ficticios.
