# Informe de seguridad V5 — reverso MOD11 ↔ MOD12

**Fecha:** 2026-10-10
**Árbol auditado:** cambios V1/V2 sin commit sobre `7552c505fc5bd0bbdcbe2c5fe9313b80a7421c7c`.
**Dictamen:** **NO GO**. Hay un [BLOQUEO] P2 de retención en la DLQ del consumidor API.
**Modo:** auditoría de solo lectura. No se modificó código ni se ejecutaron gates; los resultados de build y pruebas se citan de los informes V1/V2.

## Alcance y evidencia

Leí `AGENTS.md`, la spec completa de reverso v1.1, D4/D5/D8/D10/D11 de la spec hermana, §V5 del prompt de implementación y las skills `security-auditor` y `backend-security-coder`. Revisé los cambios de MOD11, el worker y MOD12, además de los informes de implementación V1 y V2.

Los cambios V1/V2 no están comprometidos: el SHA indicado identifica su base, no un commit que contenga el código auditado. Los gates de implementación constan como PASS en `INFORME-MOD11-MOD12-REVERSO-V1-v1.0.md` y `INFORME-MOD11-MOD12-REVERSO-V2-v1.0.md`; no los reproduje como parte de esta auditoría de solo lectura.

## Hallazgos

### [BLOQUEO][P2] La DLQ del consumidor API no aplica los 30 días de retención

`InventoryExecutionRequestProcessor.onFailed` crea el job diagnóstico con `removeOnFail: DLQ_RETENTION_SECONDS` (`apps/api/src/modules/inventory/services/inventory-execution-request.processor.ts:688-692`), donde `DLQ_RETENTION_SECONDS = 30 * 24 * 60 * 60` (`:38`). En BullMQ 5.71.0, el tipo instalado documenta que un valor numérico para `removeOnFail` es el **máximo número de jobs**, mientras que la edad se expresa como `{ age }` (`node_modules/.pnpm/bullmq@5.71.0/node_modules/bullmq/dist/esm/interfaces/base-job-options.d.ts:48-55`; versión en `pnpm-lock.yaml:177`). Así que la configuración admite hasta 2.592.000 fallidos, sin vencimiento temporal. La limpieza programada cubre `requestsQueue` y `responseQueue`, pero no `dlqQueue` (`:631-653`). Los diagnósticos no llevan el motivo ni payload, pero conservan ids/tenant y tipo de error más allá del máximo de 30 días aprobado en D11 de la spec hermana.

**Corrección requerida a `sr-backend`:** usar `removeOnFail: { age: DLQ_RETENTION_SECONDS }` (opcionalmente también `count`) y ajustar el test para afirmar la semántica temporal. Repetir el gate pertinente de worker/API y actualizar el informe R-DLQ/V2 según corresponda. Hasta entonces, retención D11 no está satisfecha.

### [P3] El diagnóstico DLQ del consumidor API omite el id de solicitud de reverso — no bloqueante

`InventoryExecutionRequestProcessor.onFailed` extrae `inventoryRequestId` del payload y construye el diagnóstico con esa clave, pero no extrae `reversalRequestId` (`apps/api/src/modules/inventory/services/inventory-execution-request.processor.ts:666-686`). Para un fallo de reverso, la DLQ resultante conserva tenant, evento y OT, pero no la correlación directa con la solicitud. No filtra el motivo ni otra PII; no afecta la integridad, autorización ni retención. Recomendación: añadir `reversalRequestId` como identificador permitido del diagnóstico para facilitar la investigación operativa.

## Dictamen

**NO GO para V1/V2 desde seguridad** hasta corregir la retención temporal de la DLQ del consumidor API y verificarla. El resto de los controles revisados —autorización/scope, aislamiento de tenant, procedencia firmada, ausencia del motivo y auditoría durable— no presenta bloqueos. La observación P3 no bloquea por sí misma. Este dictamen corresponde al árbol de trabajo sobre el SHA base indicado; debe asociarse al SHA final cuando V1/V2 se comprometan.
